Overview

The application models a two-core embedded pipeline the way an ICU monitor actually behaves: continuous acquisition, continuous analysis, and a hard guarantee that a nurse-call or automatic alarm reaches the actuator fast — no matter what the network stack is doing. Four FreeRTOS tasks on Core 1 form a producer–consumer–coordinator–actuator chain, synchronized with a queue, an event group, and a direct task notification. An independent HTTP monitor server runs on Core 0, isolated so that Wi‑Fi and HTML generation can never steal cycles from the real-time path.

01

System architecture

Four tasks, one direction of flow, Core 1 dedicated entirely to the real-time pipeline.

TASK AP8 Core 1

Telemetry Sampler

Samples ECG, heart rate, and O₂ every 50 ms and pushes one medical_telemetry_t packet onto the queue.

TASK BP8 Core 1

Arrhythmia Processor

Blocks on the queue, analyzes each sample for abnormal rhythm, and stores the latest diagnosis.

TASK CP9 Core 1

Pipeline Coordinator

Rendezvous point: waits on an event group for both the producer and consumer bits before triggering the next stage.

TASK DP12 Core 1

Alarm Dispatch Actuator

Waits on a direct task notification and immediately dispatches an automatic alarm or a manual nurse-call interrupt.

02

Engineering analysis

Four design questions, answered with the numbers that came out of the pipeline.

Why pin the web server to Core 0? What goes wrong if it's on Core 1?

The web server handles unpredictable, blocking work — Wi‑Fi I/O, HTTP requests, dashboard HTML generation — none of which has a real-time deadline. Keeping it on Core 0 leaves Core 1 dedicated to Tasks A–D, preserving deterministic scheduling and low latency. Moved to Core 1, it would compete with the real-time tasks for CPU time: scheduling delays grow, the producer or consumer can miss a deadline, queue occupancy climbs toward overflow, and alarm notifications can be delayed — exactly the failure mode this architecture exists to prevent.

Queue depth — how sized? Compute the burst rate you protect against.

Depth is 10 entries. Task A produces one packet every 50 ms (20 Hz), so 10 entries × 50 ms = 500 ms of buffered telemetry — the pipeline can absorb up to half a second of consumer stall before anything is lost. On a full queue, the producer's short-timeout xQueueSend() fails and the dropped_samples counter increments rather than blocking Task A past its 50 ms deadline. The consumer (Task B) waits up to 100 ms for a new reading before timing out. Together this guarantees FIFO delivery while protecting the sampler's real-time deadline over strict data completeness.

Event group vs. N semaphores — when is each better?

An event group wins when a task must wait for multiple conditions at once — exactly Task C's job: it needs both the "produced" bit from Task A and the "processed" bit from Task B before it can proceed. That's an AND-wait, which is what event groups are built for. N semaphores are the better fit for signaling a single event or gating access to a shared resource, not for a multi-condition rendezvous like this one.

Direct notification vs. binary semaphore — measure both wakeup latencies.

Benchmarked on an ESP32‑S3 (Wokwi) by triggering an ISR on a GPIO button press and timing the wakeup of each mechanism, eight runs each.

Direct task notificationavg 28.9 µs
Binary semaphoreavg 520 µs
Notification range 20–32 µs · Semaphore range 152–793 µs · semaphore was ~18× slower (520 / 28.9)

Direct notifications write straight into the receiving task's TCB, skipping the kernel-object overhead a binary semaphore carries as a queue-based give/take. For strict one-to-one signaling — Task D waiting on a single source — direct notification is the right call. Binary semaphores remain the better tool when multiple tasks wait on the same event or a distinct synchronization object is genuinely needed.
